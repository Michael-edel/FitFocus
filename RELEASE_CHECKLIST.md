# Проверка и выпуск FitFocus

Обновлено: 09.10.2026. Это шаблон следующего выпуска, а не отчёт о пройденных
проверках. Для релиза записать ветку, полный SHA, PR, URL CI и адрес среды.
Область текущей документации: [карта](docs/README.md).

## Код готов к проверке

- [ ] Ветка основана на актуальном `origin/main`; зависимости от PR #90 явны.
- [ ] Diff содержит только заявленное изменение, без секретов и лишних файлов.
- [ ] Для исправления есть проверка воспроизводившегося дефекта.
- [ ] Обновлены задачи, решения и затронутые API/storage-контракты.
- [ ] Указаны изменения формата, старые клиенты и порядок миграции.

Для изменения исполняемого кода запускать проверки из `package.json`
и действующего `.github/workflows/ci.yml`:

```text
npm ci
npm audit
npm run check:schema
npm run check:privacy
npm run check:auth-scope
npm run check:api-invariants
npm run check:admin-guards
npm run test:unit
npm run typecheck
npm run typecheck:domain-strict
npm run typecheck:storage-strict
npm run build
npm run test:e2e
```

Для E2E предварительно установить браузеры Playwright. Python нужен для
schema/privacy. Для изменения только документации достаточно проверки diff,
ссылок, фактов и отсутствия случайных изменений кода; обязательный CI остаётся
обязательным. Не переносить старые результаты тестов на новый SHA.

## GitHub CI

- [ ] Проверки действительно запустились на SHA кандидата или его merge ref.
- [ ] Зафиксированы итог каждого обязательного job и причина каждого skip.
- [ ] Падение исправлено или выпуск остановлен с явно записанной причиной.
- [ ] Deploy в Cloudflare не используется как замена CI.
- [ ] Сканирование секретов охватывает историю, необходимую для этого выпуска;
  neutral/skipped GitGuardian не трактуется как чистый результат.

Если workflow не стартовал: проверить событие, branch/path filters, настройки
Actions, наличие workflow в нужной ветке и состояние PR. Не заявлять успех
по одному факту push. Для большого PR #90 проверить объём и реальный охват
проверок; не обходить блокировки отключением защит.

## Staging и данные

- [ ] Для P0.7 выполнены [условия выпуска поколений state](docs/state-generations.md#условия-выпуска-и-отката):
  миграция 0019 предшествует серверу; клиент понимает tombstones/409/ack;
  старые writers остановлены, поколения старых pending-операций не угаданы.
- [ ] Подтверждены отдельный адрес среды, D1 binding и безопасные тестовые данные.
- [ ] Preview не перенаправляет тест в production: проверить редирект
  неканонических `*.pages.dev` в `index.tsx`.
- [ ] Создана резервная копия затрагиваемых данных; восстановление проверено.
- [ ] Миграция проверена на старой схеме и повторном запуске; schema/privacy
  охватывают новые данные, включая tombstones и миграционные записи.
- [ ] Старые/новые клиенты проверены в порядке предполагаемого выпуска.
- [ ] Для IDB старый и новый build работают на одном origin в одном browser
  context; разные preview-hostnames не заменяют этот тест.
- [ ] Проверены `blocked`, закрытие старых вкладок, reload, quota, abort,
  повторный вход, два аккаунта, две вкладки и потерянный ответ сервера.
- [ ] Для изменённых интеграций есть реальный smoke в тестовой среде;
  mock OAuth/D1/push/Stripe не объявлен проверкой реального сервиса.

Наличие staging, доступ к production D1 и успешное восстановление копии
не подтверждены этим пакетом документов.

## Выпуск и наблюдение

- [ ] Зафиксированы release SHA, версии схемы и совместимый клиент.
- [ ] При несовместимой записи определены безопасный порядок и ограничение доступа
  старых клиентов; feature flag сам по себе не мигрирует их IDB.
- [ ] Проверены вход, чтение/локальная запись, sync, конфликт и удаление/recreate.
- [ ] Наблюдаются ошибки API, возраст pending/sending, conflicted/failed,
  неизвестные записи миграции и состояние `blocked`.
- [ ] Определены критерии остановки, ответственный и время проверки после выпуска.

## Откат

- [ ] Старый код умеет читать данные, уже записанные новой версией, либо
  описан безопасный путь вперёд и ограничение старого кода.
- [ ] Откат не стирает неподтверждённые операции, legacy-источник и карантин.
- [ ] Для серверной миграции описано восстановление без потери новых записей;
  восстановление старой копии не считается автоматически безопасным.
- [ ] После отката подтверждены данные, доступ и состояние синхронизации.
