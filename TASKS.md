# Стабилизация и развитие FitFocus

Обновлено: 09.10.2026. Проверенная ревизия: `810adb1`, полная область снимка
в [карте документации](docs/README.md). Этот файл — очередь реализации.
Согласованный план не равен готовому коду. Ни один P0 ниже пока не закрыт.

## Порядок работы

Начать с P0.1. Затем реализовать фундамент P0.8 и поведение P0.2–P0.6
небольшими зависимыми изменениями. Серверная часть P0.7 нужна до приёмки
сценариев удаления и повторного создания. P0.9 пополняется тестами вместе
с каждым исправлением, а завершается проверкой всего жизненного цикла.

Новые независимые ветки начинать от актуальной GitHub `origin/main`.
Если нужны изменения из PR #90, сначала выделить или интегрировать
необходимую зависимость и явно указать её в PR. Не отправлять локальную
`main` целиком: на дату снимка она опережает `origin/main` на 250 коммитов.

### P0.2 — сохранить конфликт и ошибочную операцию

- [ ] При 409 сохранить локальный payload, серверный снимок и намерение delete.
- [ ] Переводить операцию в `conflicted`, не считать её отправленной.
- [ ] Неповторяемые 4xx хранить как `failed`; 408/429/5xx и сетевые сбои
  обрабатывать по политике ограниченных повторов.

Готово, когда update/delete-конфликты и failed-операции доступны после reload;
совпадение текущего локального значения с исходящей записью не скрывает конфликт.

### P0.3 — разделить локальную запись и паузу отправки

- [ ] После 401 продолжать сохранять новые операции, остановив отправку.
- [ ] После подтверждённого входа в тот же аккаунт снять auth-паузу.
- [ ] Различать 403 `ACCESS_REQUIRED` и `FORBIDDEN_KEYSPACE`; повторный вход
  не считать универсальным исправлением 403.

Готово, когда изменения, сделанные во время auth-паузы, не теряются и
после входа отправляются только от подтверждённого владельца.

### P0.4 — защитить локальные изменения при загрузке облака

- [ ] Перед применением cloud snapshot проверять pending/sending/conflicted
  операции и локальную ревизию для этого аккаунта и ключа.
- [ ] Проверить `sessionHydration.ts`, `profileSync.ts` и repository отдельно.
- [ ] Не заменять локальный снимок и не менять его baseVersion только потому,
  что пришла более новая облачная версия.

Готово, когда повторный вход и восстановление сети сохраняют локальные
изменения; конфликтующие полные JSON-снимки не сливаются автоматически.

### P0.5 — защититься от запоздавших ответов

- [ ] Привязать ответ к opId, accountId, sessionEpoch, attemptId и ревизии.
- [ ] Проверять принадлежность и менять операцию/версию одной IDB-транзакцией.
- [ ] Разрешать передачу подтверждённой версии следующей операции только
  при доказанной причинной зависимости; независимую правку другой вкладки
  автоматически не перебазировать.

Готово, когда ответ старого запроса не удаляет новую операцию, не применяет
старый payload и не продвигает версию независимо изменённого снимка.

### P0.6 — аккаунты и несколько вкладок

- [ ] Хранить постоянного владельца операции, изолировать чтение/отправку по нему.
- [ ] Новая сессия того же аккаунта может возобновить его старую очередь;

- [ ] Проверить две вкладки без Web Locks, конкурентные записи разных и

Готово, когда нет отправок чужих данных и потери записи из-за перезаписи
всей очереди одной вкладкой.

### P0.7 — непрерывные серверные версии после удаления

- [ ] Спроектировать совместимое расширение `user_kv` и API: tombstone
  или эквивалентная сохранённая генерация после удаления.
- [ ] Зафиксировать смысл baseVersion=0 для create/delete и старых клиентов.
- [ ] Выполнять CAS и получать подтверждённую версию атомарно через `RETURNING`.
- [ ] Проверить delete → recreate → stale update, гонку пакетной записи,
  миграцию, экспорт и удаление аккаунта на staging.

Готово, когда устаревшая версия не становится действительной после recreate,
а версия в ответе принадлежит именно подтверждённой мутации.

### P0.8 — единая постоянная очередь в IndexedDB

Первый компонент реализован в `storage/legacyQueue.ts`: нормализация всех
согласованных случаев и fingerprint по JSON-массиву с SHA-256. 62 unit-проверки
и все три режима typecheck прошли после исправления сужения типа в тестовом
помощнике (первый CI выявил TS2339). Компонент пока не подключён к runtime;
ни импорт legacy, ни смена хранилища очереди этим шагом не завершены.

В [PR #93](https://github.com/Michael-edel/FitFocus/pull/93) добавлен общий
менеджер схемы IDB v2 и транзакционный API DurableOutbox. Существующее
хранение объёмных values использует этот менеджер; UserStateRepository
и сетевой отправитель пока не переведены на новую очередь. Создание stores
миграции само по себе не означает выполнения импорта.

- [x] Обновить существующую IDB до v2, сохранив values; создать outbox,
  migration_items, migration_unknown и outbox_meta.
- [x] Реализовать и проверить транзакционные примитивы записи value/операции,
  claim/lease и guarded finish, явное владение ключом и сессией.
- [ ] Реализовать [ADR-005](docs/adr/ADR-005-durable-outbox.md), включая
  нормализацию legacy, карантин, атомарный импорт и возобновляемую миграцию.
- [ ] Подключить UserStateRepository и отправитель к новой очереди;
  связанные values/операции сохранять транзакционно во всех новых writers.
- [ ] Подключить состояния blocked, quota/abort и недоступности IDB к UI;
  не сообщать об успехе и не создавать localStorage-outbox при отказе.
- [ ] Проверить старую и новую сборку на одном origin в одном browser context.

Готово, когда IDB — единственный источник очереди, в том числе без Web Locks;
legacy-ключ не используется для новой очереди и не удаляется до проверенного
импорта. Неизвестное владение не определяется по активному аккаунту.

## Как закрывать задачу

Для выполненного пункта указывать commit/PR, затронутые контракты,
проверенные сценарии и ограничения. Обновлять документы в том же изменении.
Зелёный deploy не заменяет зелёный CI; skipped/neutral проверка не считается
подтверждением отсутствия ошибок или секретов.
