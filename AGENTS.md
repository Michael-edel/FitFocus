# Инструкции для помощника FitFocus

Обновлено: 12.10.2026. Область: весь репозиторий.

## Начало работы

- Прочитай [README](README.md), [TASKS](TASKS.md) и относящийся к задаче
  контракт. Порядок разработки и проверок: [CONTRIBUTING](CONTRIBUTING.md).
- Для поиска реализации функции используй [карту кода](docs/code-map.md),
  затем проверь актуальные исходники и тесты выбранной ветки.
- Сверь [текущий статус](docs/project-status.md) с HEAD и рабочим деревом.
  Не приписывай незакоммиченным изменениям результаты CI прежнего SHA;
  исторические документы сохраняют границы указанной в них ревизии.
- Установи фактическую ветку, HEAD, базу PR и наличие пользовательских правок.
  Не перезаписывай чужую работу. Проверяй исходники своей ветки: описанные
  модули PR #90 могут отсутствовать в main.
- Следуй текущему запросу пользователя. Не расширяй продуктовую задачу
  новой архитектурной переработкой без необходимости.

## Ориентиры в коде

- `App.tsx`, `ui/`, `features/` — клиент и сценарии, если каталог есть в ветке.
- `domain/` — доменные расчёты; `storage/` — локальное хранение и очередь.
- `functions/api/` — Pages Functions; `_lib/` — общие серверные сценарии.
- `db/schema.sql`, `migrations/` — серверная схема и миграции.
- `tests/`, `e2e/`, `scripts/` — проверки; `sw.ts`, `pwa.ts` — PWA.

## Сохранность данных

- Сверяй изменения синхронизации с [моделью](docs/sync-model.md)
  и [ADR-005](docs/adr/ADR-005-durable-outbox.md).
- Сохраняй локальное намерение при конфликте; auth-пауза останавливает
  отправку, но не сохранение новых изменений.
- Не угадывай accountId legacy-записи по текущему входу. Поздний ответ
  должен относиться к своей операции, попытке, аккаунту и сессии.
- Цель P0.8 — одна IDB-outbox, атомарные данные/операция и импорт/ledger.
  Наличие Web Locks не выбирает хранилище. Пятнадцать управляемых ключей
  используют атомарные value/операции; sender использует свежий /me proof,
  server session guard и claim/finish. Прежний Map sender удалён из текущей
  сборки; это не барьер для старых сборок. Редактор существующего profile
  использует ту же outbox с resource: profile и отдельным guarded HTTP;
  черновик формы не считается сохранённым при отказе commit. Регистрация
  сохраняет canonical profile до AI, затем причинный update; owned IDB-профиль
  восстанавливается без подбора по email или переноса prefix. HTTP bootstrap,
  state-hydration и profile seed используют scope/readGuard и транзакционный
  auth-fence (`dac2de2`); остальные callbacks и runtime legacy ещё открыты.
  Контракт и приёмка компонента:
  [загрузка сессии](docs/bootstrap-hydration.md). Проверенная граница:
  [регистрация](docs/registration-persistence.md),
  [сохранение профиля](docs/profile-persistence.md),
  [подключение остальных state-записей](docs/owned-state-writers.md),
  [sender](docs/state-sender.md),
  [текущий клиент](docs/runtime-state.md),
  [фундамент P0.8](docs/outbox-implementation.md).
- Повторное чтение идентичного owned-снимка с той же серверной версией
  не повышает локальную revision. Новая версия всё равно делает независимый
  редактор устаревшим. Не пропускай проверки pending, epoch и auth-fence.
- Подтверждённый отказ `/me` и неверный протокол останавливают вход;
  транспортная ошибка/408/429/5xx допускают только чтение собственных локальных
  данных. Не объединяй эти исходы в общий fallback.
- Компонент [legacy-импорта](docs/legacy-migration.md) уже реализован на
  `51a789c`, но `verifiedOwners` и `writersStopped` должны получать доказательства
  из будущей интеграции. Сам флаг не останавливает старые вкладки.
- Не удаляй legacy-источник, карантин или pending-записи ради успешного
  статуса миграции. Ошибку хранения не показывай как успешное сохранение.
- Серверный [AI/items guard](docs/ai-session-guard.md) на `16d3c34` проверяет
  переданную account/session-привязку до прикладных эффектов. Персональный
  menu-сценарий подключён на `f4b4eee`; остальные callbacks ещё открыты.
  Не переноси CI прежнего `8fc0b1b` на эту реализацию; сверяй точный HEAD.
  Требуй свежий proof, capabilities, lifetime и атомарный profile commit.
  Личные покупки на `4736ff5` следуют profile CAS через SQL-проекцию;
  [контракт](docs/personal-menu-projection.md), [ADR-007](docs/adr/ADR-007-personal-menu-projection.md).
  Порядок промежуточного серверного выпуска и границы локальных проверок —
  в [инструкции перехода 0020](docs/profile-cas-rollout.md).
  Не возвращай отдельный личный items POST. Семейный CAS реализован
  на `405238b`; его PWA/lifecycle-приёмка и выпуск ещё открыты.
  Scope не обеспечивает CAS произвольной вторичной проекции;
  запросы прежнего клиента без scope остаются незащищёнными этим guard.
- Автоматический profile debounce вызывает `flushPending`, ручная синхронизация —
  `syncNow` со свежим proof. Не переавторизуй auth-паузу таймером; сохраняй
  проверки account/epoch/readGuard и постоянные операции.
  [Контракт](docs/state-sender.md#автоматическая-отправка-и-ручная-проверка-сессии).
- Серверный компонент [P0.7](docs/state-generations.md) проверен отдельно
  на `237f862` в PR #94 и объединён с этой веткой коммитом `93f90c0`.
  До совместного CI и staging не объявляй всю систему готовой. Для ack требуется protocol 2 и версия своей
  мутации; не вычисляй её как baseVersion+1 и не возвращай физический DELETE.

- Достижения получают исходный login proof из hydration, затем свежий proof
  каждой HTTP-попытки. Не подменяй его текущим IDB/cookie-входом при задержке
  или pageshow; старый callback должен обращаться только к своему клиенту.
  [Контракт и границы](docs/achievement-session.md).
- Семейный `useFamilyCloud` получает исходный login guard, обновляет его proof
  перед каждым HTTP и сохраняет scope своих React-setters. Не подбирай текущую
  сессию для старого callback. [Контракт](docs/family-session.md) отдельно отмечает
  историю прежнего AI-пути на `9c44c21`. В текущей рабочей реализации
  [семейное меню](docs/family-menu-state.md) использует ту же outbox, family/week
  CAS и guarded commit; локальный v2/v3 bundle smoke не подтверждает SW/PWA и выпуск.
  [ADR-008](docs/adr/ADR-008-family-menu-generation.md) требует SQL-барьер старых
  writers и versioned IDB v3; не понижай/не удаляй IDB при откате.
  Account/session guard не фиксирует членство и целевую семью мутации.
- Автоматическое обновление read proof передаёт исходный guard в IDB-транзакцию
  принятия сессии. Поздний proof не снимает auth-паузу. Не удаляй эту проверку
  ради успешной отправки; явная проверка sender имеет отдельный контракт.

  сообщи конкретно, без заявления о состоявшемся слиянии.
- Не сохраняй секреты или пользовательские данные в коде, документах и логах.
