# Работа с FitFocus

Обновлено: 09.10.2026. Начальная навигация: [карта документации](docs/README.md).
Это инструкция для разработки; результаты выполненных проверок хранятся
отдельно в [журнале стабилизации](docs/stabilization-progress.md).

## Перед изменением

Прочитайте соответствующий пункт [TASKS](TASKS.md), контракт и исходники
именно выбранной ветки. Документация архитектуры закреплена за ревизией
из PR #90; в GitHub main часть этих модулей пока отсутствует.

Проверьте текущую ветку, незакоммиченные изменения и актуальную базу.
Независимое изменение начинайте от актуального origin/main. Если нужна
непринятая зависимость, укажите её PR и используйте его ветку как базу
до интеграции. Документация PR #91 зависит от исправления CI PR #92.
Большую локальную main нельзя отправлять поверх GitHub main без проверки
всего отличающегося набора изменений.

## Установка и клиент

В CI используются Node.js 24 и Python 3.12. Python запускает проверки
схемы и приватности. В корне проекта выполните:

```text
npm ci
npm run dev
```

Используйте зафиксированный package-lock.json. При изменении зависимостей
обновляйте lockfile вместе с package.json и проверяйте npm audit.
Скрипты predev/prebuild/pretypecheck/pretest:unit генерируют сведения
о сборке; ручное редактирование сгенерированного файла не требуется.

Клиент работает на http://localhost:5173. Vite отправляет `/api` на
http://localhost:8788; в Docker-режиме цель — http://wrangler:8788.
Запуск только Vite не запускает D1, OAuth или серверные функции.

## Локальные серверные функции

Конфигурация Pages/D1 находится в `wrangler.toml`, binding базы — `DB`,
миграции — в `migrations/`. Wrangler не включён в package.json:
следующие команды предполагают доступный и настроенный Wrangler.

```text
npm run build
npx wrangler d1 migrations apply fitfocus --local
npx wrangler pages dev dist --port 8788 --ip localhost
```

После запуска backend запустите Vite в другом терминале. Эти команды
описывают локальный путь проекта; настоящий запуск OAuth/D1 в текущей
сессии не подтверждён. Перед обращением к удалённой базе отдельно проверьте
окружение и [чек-лист выпуска](RELEASE_CHECKLIST.md).

Шаблоны `.env.example` и `.env.local.example` перечисляют часть настроек.
Для клиента используются только публичные значения. Server secrets задаются
в среде backend; файл Vite .env.local сам по себе не настраивает Pages Functions.
Приватные ключи, токены, реальные .env и пользовательские данные не должны
попадать в Git, Markdown, скриншоты и логи. Не помещайте server secrets
в переменные с префиксом VITE_.

## Проверка изменения

Команды берите из текущих `package.json` и `.github/workflows/ci.yml`.
Полный набор для кандидата на выпуск приведён в
[RELEASE_CHECKLIST](RELEASE_CHECKLIST.md#код-готов-к-проверке).

Во время разработки сначала воспроизведите дефект и проверьте затронутый
сценарий. Для изменений storage запускайте storage-strict, для domain —
domain-strict, для API — соответствующие инварианты, схему и приватность.
Не отключайте проверку ради зелёного результата.

Для браузерных проверок после npm ci установите браузеры:

```text
npx playwright install chromium firefox webkit
npm run test:e2e
```

Playwright запускает production build и preview. На Linux для чистой среды
CI используется install --with-deps. При прогоне зафиксируйте SHA,
прошедшие/пропущенные сценарии и ошибки консоли. Mock API проверяет
клиентский сценарий; реальную интеграцию подтверждает отдельный staging smoke.

Для изменений только Markdown проверьте ссылки, якоря, согласованность фактов,
diff и отсутствие случайных изменений исполняемого кода. Обязательные
GitHub checks остаются обязательными.

## Коммит, PR и CI

Один набор изменений должен иметь ясную цель и проверяемый diff. В описании
PR укажите проблему, итоговое поведение, базовую зависимость при наличии,
проверки и оставшиеся ограничения. Выполненные пункты TASKS связывайте
с commit/PR; не закрывайте весь P0 по готовности одного компонента.

После push проверьте запуск workflow и результат на точном HEAD или
соответствующем merge ref. Старый зелёный запуск и успешный Cloudflare deploy
не подтверждают новый CI. Если проверка упала, изучите её лог и исправьте
причину в рамках изменения. Не обходите защиту main и не используйте force push
как обычный способ доставки исправлений.

## Какие документы обновлять

| Изменилось | Документ |
|---|---|
| Пользовательская функция или её готовность | PRODUCT.md |
| Статус, зависимость или критерий задачи | TASKS.md |
| Проверки конкретной ревизии | docs/stabilization-progress.md |
| API state/profile | API_CONTRACTS.md |
| Хранилище, версия схемы, владение | docs/data-model.md и затронутый ADR |
| Очередь, конфликт, retry, сессии | docs/sync-model.md, ADR-005 и docs/outbox-implementation.md |
| Legacy-формат, импорт, ledger или карантин | docs/legacy-migration.md и относящиеся пункты TASKS |
| Существенное архитектурное решение | DECISIONS.md и новый/изменённый ADR |
| Порядок выпуска или отката | RELEASE_CHECKLIST.md |

Каждый статус должен различать «согласовано», «реализовано в ветке»,
«проверено», «слито» и «выпущено». Старые результаты сохраняйте с их SHA,
добавляя новые свидетельства, а не перенося числа тестов на другой код.
