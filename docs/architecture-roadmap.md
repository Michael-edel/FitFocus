# Архитектурная переработка FitFocus

Документ фиксирует порядок безопасной переработки без «большого взрыва». Каждая
итерация должна оставлять приложение запускаемым, сопровождаться тестами и
выходить отдельным pull request.

## Принципы

- Сохранять действующие API, ключи browser storage и D1-схему, пока потребитель
  не переведён на новую границу.
- Делать локальную запись перед фоновой синхронизацией с облаком.
- Не переносить бизнес-правила в React-экраны или HTTP routes.
- Измерять ошибки, задержки и конфликты до и после изменения.

## Очередь работ

1. **Границы фронтенда.** Вынести profile, diary, AI и family в feature-модули;
   оставить в `App.tsx` shell, сессию и навигацию.
2. **Хранилище.** Перевести данные дневника, истории и настроек на typed
   repositories с сохранением текущего формата ключей. Затем перенести объёмные
   данные в IndexedDB и добавить надёжную outbox-очередь.
3. **Серверные use cases.** Сделать Pages routes HTTP-адаптерами, а правила
   профиля, семейного доступа, квот и платежей перенести в application/domain.
4. **Надёжность внешних интеграций.** Ввести единый HTTP-клиент с timeout,
   классификацией ошибок и безопасными ограниченными повторами.
5. **Наблюдаемость.** Добавить request ID, структурированные события,
   dashboard/alerts для API, синхронизации, AI и платежей.
6. **Данные и выпуск.** Нормализовать критичные части profile JSON, расширить
   контрактные и мобильные smoke-тесты, выпускать изменения под feature flags.

## Первый срез

В этом изменении вводятся `UserStateRepository` и `useProfilePersistence`.
Репозиторий уже обслуживает дневник, историю, настройки, избранные рецепты и
последний AI-совет. `features/diary` обслуживает выбор дня, итоги и действия с
записями и историей. Операции семьи сведены в `features/family/familyApi.ts`,
а подготовка данных AI-советника — в `features/ai`. UI-хуки управляют только
состоянием и сценариями экрана. Все новые границы используют существующие
ключи `fitfocus_data_<user>_*` и текущий механизм синхронизации, поэтому не
требуют миграции пользовательских данных.

Репозиторий пользовательских данных теперь связывает каждый ключ с типом
значения при записи. Некорректные данные не попадают в локальное хранилище и
очередь фоновой синхронизации из-за ошибки в вызывающем коде.

Очередь фоновой синхронизации хранится в browser storage до успешного ответа
сервера. После перезагрузки она возобновляется, когда пользовательская сессия
готова; изменения одного ключа по-прежнему объединяются в последнюю операцию.

Семейный API использует общий browser HTTP-клиент: GET-запросы имеют тайм-аут
и один ограниченный повтор при временной ошибке. Изменяющие запросы не
повторяются автоматически, чтобы избежать повторной записи на сервере.

Проверка запросов синхронизации вынесена из `/api/state` в server use case.
Маршрут остаётся HTTP-адаптером, а правила формата, версии и допустимого
пространства ключей тестируются отдельно от D1.

Атомарная запись и удаление состояния также вынесены в слой D1 use case;
маршрут не содержит SQL-правил сравнения версий и обработки конфликтов.

Чтение синхронизируемого состояния вынесено в общий use case для `/api/state`
и bootstrap; оба сценария фильтруют запрещённые ключи, включая старые
локальные снимки `_all_users`.

Команды изменения профиля используют отдельный server use case: он фильтрует
поля клиента, сохраняет защиту keyspace, проверяет версию, определяет план на
сервере и выполняет CAS-запись. PUT и PATCH остаются HTTP-адаптерами.

Загрузка профиля вынесена в общий read use case для `/api/profile` и
`/api/bootstrap`; идентификатор, тариф и миграция прежней учётной записи
вычисляются одинаково во всех сценариях входа.

Синхронизация состояния получает сквозной `X-Request-ID`: браузер добавляет
его к запросу, сервер возвращает в ответе и пишет компактное структурированное
событие с кодом результата без тел запросов и идентификатора пользователя.

Синхронизация профиля использует тот же browser HTTP-клиент: для каждого
запроса добавляется `X-Request-ID`, действует единый тайм-аут, а профильный
маршрут возвращает идентификатор и пишет структурированное событие ответа.

Стартовый запрос bootstrap использует безопасный повторяемый GET-транспорт и
передаёт `X-Request-ID`; сервер возвращает идентификатор и фиксирует исход
гидратации без данных пользователя.

Еженедельные AI-отчёты теперь также используют `UserStateRepository`: формат
ключа и данных сохранён, а записи проходят через локальное сохранение и
долговечную очередь фоновой синхронизации.

Сценарий AI-совета вынесен из `App.tsx` в feature-хук: проверка тарифа,
формирование контекста, запись результата, учёт использования и проверка
достижения выполняются как единый тестируемый use case. Экран сохраняет только
состояние отображения карточки и индикатора загрузки.

Проверка сессии и кода приглашения в браузере также используют общий HTTP
транспорт: безопасное чтение имеет ограниченный повтор, а изменяющая POST-
проверка не повторяется автоматически, но получает тайм-аут и request ID.

Обработка фото еды вынесена в AI feature: сжатие, анализ, локальная запись
дневника, отображение результата и учёт использования тестируются отдельно от
экрана. Пакет изображений ограничивается оставшимся дневным лимитом, поэтому
массовая загрузка не может его обойти. Неизвестный или повреждённый тариф
обрабатывается как отсутствие доступных сканирований.

Генерация личного недельного меню стала отдельным AI-сценарием: feature
управляет индикатором, понятной ошибкой, сохранением обновлённого профиля и
сигналом достижения. Экран плана получает готовый обработчик и состояние.

Контекст недельного AI-отчёта строится одним feature-builder для фоновой
генерации и ручного повтора. Это исключает расхождение данных между путями.

Ошибка сжатия или анализа одного фото записывается отдельно и не отменяет
обработку остальных файлов выбранного пакета.

Повтор AI-действий вынесен в use case с независимыми проверками для совета,
плана, объяснения плато и недельного отчёта. Действие из устаревшей записи
другого пользователя больше не запускается в текущей сессии.

Фоновая генерация недельного AI-отчёта теперь выполняется в feature-хуке:
дедупликация, сохранение последнего действия, обновление отчётов и обработка
ожидаемых ошибок не остаются в корневом экране.

Сброс дневных и недельных квот вынесен в чистый usage-сценарий. Он использует
общие календарные ключи вместо форматирования даты через локаль браузера.

Избранные рецепты получили отдельный feature: он восстанавливает прежние
форматы данных, сохраняет нормализованный результат через typed repository и
держит ограничение списка в 100 записей.

Состояние курса вынесено в feature-хук: выбранный урок, открытый просмотр и
выбранный вариант теста сохраняются и восстанавливаются отдельно для каждого
пользователя.

Настройки профиля также вынесены в feature-хук. При смене пользователя запись
приостанавливается до завершения загрузки, поэтому настройки прошлого профиля
не могут затереть сохранённые настройки текущего.

Состояние поиска еды стало отдельным feature-хуком и поддерживает прежний
текстовый формат сохранения наряду с JSON-состоянием, не теряя запросы после
обновления приложения.

Настройки панели метаболической адаптации теперь гидратируются как единое
состояние на пользователя. Отсутствующие ключи нового профиля сбрасываются в
безопасные значения и больше не наследуют выбор предыдущего пользователя.

Отметки выполненных задач плана также вынесены в feature-хук. Запись в
локальное и синхронизируемое хранилище начинается только после загрузки
активного профиля, поэтому задачи не переносятся между учётными записями.

Гидратация предпочтений семейного меню теперь валидирует все поля и строит
пустое состояние из текущего состава семьи. Новый профиль больше не получает
режим готовки, бюджет или валюту от предыдущего пользователя.

Черновик веса на dashboard и флаг включения дневника питания в PDF объединены
в профильный feature-хук. Оба значения загружаются до следующего сохранения и
не могут записать настройки прошлого пользователя в текущий профиль.

Предпочтение фронтальной или основной камеры вынесено из `App.tsx`. Feature
нормализует устаревшие значения и не блокирует следующее пользовательское
сохранение после сброса интерфейса.

Сохраняемое состояние экрана плана теперь обслуживается единым feature-хуком:
режим личного или семейного плана, раскрытые дни, правила и окно настроек
семьи. Формат существующего ключа хранения сохранён, а новые дни меню получают
предсказуемые значения по умолчанию.

Код приглашения теперь гидратируется и сохраняется отдельным auth feature.
При смене или завершении сессии значение очищается, поэтому новый профиль не
может получить код приглашения предыдущего пользователя.

Расписание refeed вынесено в adaptation feature: дата рассчитывается для
следующего локального дня, синхронизируется прежним ключом и очищается при
смене активного профиля.

Обновление профиля участника семьи вынесено из HTTP-маршрута в server use case.
Он нормализует входные ограничения, проверяет активное семейное членство и
изменяет только строку текущего пользователя.

Выпуск семейного приглашения также стал server use case: он подтверждает роль
владельца и семейный тариф, ограничивает срок действия и повторяет генерацию
кода при конфликте уникальности.

Присоединение к семье по приглашению теперь выполняет отдельный server use
case. В одной операции он проверяет код и тариф владельца, ограничивает размер
семьи, атомарно закрепляет приглашение и откатывает его при конфликте записи.

Создание семьи вынесено из маршрута в server use case. Он проверяет семейный
тариф, создаёт владельца только при отсутствии активного членства и удаляет
созданную семью, если конкурентная операция заняла членство раньше.

Чтение текущей семьи и её активных участников также выполняется server use
case, который всегда ограничивает результат активным членством вызывающего
пользователя.

Проверка API-инвариантов теперь анализирует маршруты вместе с вынесенными
server use cases, поэтому декомпозиция не ослабляет контроль атомарных семейных
операций и ограничений доступа в CI.

Семейные API-маршруты получили единый ответ с `X-Request-ID` и структурное
событие без данных запроса. Чтение, создание, приглашение, присоединение и
изменение участника теперь можно связать с конкретным серверным событием.

Сквозная трассировка расширена на семейное недельное меню: чтение, сохранение
и генерация отвечают тем же `X-Request-ID` и создают отдельные события исхода.
Проверка API-инвариантов распознаёт этот общий ответ, сохраняя контроль
валидации даты недели после рефакторинга маршрутов.

Мобильные и PWA smoke-тесты запускают production preview через активный
Node/npm-процесс. Поэтому один и тот же набор сценариев воспроизводимо
проверяет браузер, Android и iPhone/PWA в локальной среде и CI.

Список покупок использует общий трассируемый JSON-ответ. Чтение, единичные и
пакетные отметки, а также сохранение недельных позиций возвращают `X-Request-ID`
и записывают событие без содержимого запроса.

Чтение и сохранение недельного семейного меню вынесены из HTTP-маршрута в
server use cases. В них сосредоточены проверка активного семейного доступа,
тарифа, формы меню и безопасная запись D1; маршрут отвечает только за транспорт.

Сохранение позиций недельного меню также стало server use case: семейные права,
нормализация ингредиентов, ограничение входного списка и пакетная замена D1
выполняются вне HTTP-адаптера.

Одиночная и пакетная отметка покупок объединены в server use case. Он сохраняет
разные гарантии записи: одиночная операция делает UPSERT, а пакетная выполняется
одним D1 batch после проверки семейного доступа и нормализации ингредиентов.

Чтение списка покупок стало отдельным read use case: он проверяет семейный
доступ, объединяет повторяющиеся ингредиенты и применяет сохранённые отметки
одинаково для личного и семейного режима.

Генерация семейного меню вынесена в server use case вместе с расчётом порций,
учётом ограничений продуктов и одной атомарной записью меню, порций и списка
покупок. HTTP-маршрут оставляет только проверку сессии, параметра недели и ответ.

Административное изменение обращения в поддержку теперь выполняется отдельным
use case: он валидирует статус, приоритет и назначение, а ответ, изменение заявки
и audit event сохраняет единым D1 batch.

Детерминированный AI fallback отделён от HTTP-маршрута: загрузка безопасного
снимка профиля, расчёт калорий и подготовка ответа при недоступности провайдера
теперь тестируются как самостоятельный сценарий.

Создание обращения в поддержку и его первое сообщение теперь записываются одним
D1 batch. Это исключает частичную запись заявки без исходного сообщения при
сбое между двумя операциями.

Отбор получателей административной push-рассылки вынесен в чистый сценарий:
явный список пользователей, сегменты, сортировка и пагинация теперь проверяются
до вызова внешнего push-провайдера и независимо от HTTP-маршрута.

Преобразование AI-запроса для OpenAI вынесено в отдельный адаптер провайдера.
Он одинаково нормализует текст, изображения, JSON-схемы и отключает хранение
перед передачей внешнему сервису.

AI-маршрут возвращает сквозной `X-Request-ID` на каждом ответе и фиксирует
безопасное структурированное событие с кодом результата. Это позволяет связать
проблему клиента с серверным исходом без записи текста запроса или профиля.

Выполнение административной push-рассылки вынесено в server use case: он держит
ограниченную параллельность, удаляет недействительные подписки и фиксирует
результаты доставок одним D1 batch.

Административная push-рассылка получила сквозной `X-Request-ID` и событие
исхода без полезной нагрузки уведомления. Это делает dry-run и фактическую
рассылку наблюдаемыми без раскрытия данных получателей.

Административный маршрут больше не содержит устаревшие локальные модели и
функции сегментации получателей: он использует типы и нормализаторы общего
сценария отбора. Это оставляет единые правила фильтрации и пагинации для
предпросмотра и реальной рассылки.

Вызов AI-провайдера вынесен в адаптер: он применяет ограниченный таймаут,
безопасно разбирает ответ и повторяет запрос только для недоступной Gemini
модели. HTTP-маршрут сохраняет контроль квот, кеша, fallback-ответов и событий.

Чтение обращений для администратора стало отдельным read use case: загрузка
карточки, безопасных URL вложений, цепочки сообщений и очереди со статусным
фильтром выполняется вне HTTP-обработчика.

Административная карточка пользователя также выделена в read use case. Он
собирает и нормализует профиль, роли, семейный статус, подписку, сессии и
сводку AI, а маршрут оставляет только проверку доступа и HTTP-ответ.

Объёмные пользовательские записи — дневник, история, недельные отчёты,
избранные рецепты и последняя AI-карточка — переносятся в IndexedDB с ленивой
миграцией прежних ключей. Очередь синхронизации и версии D1 сохранены: после
надёжной записи в IndexedDB операция отправляется через прежний cloud outbox,
а при недоступности IndexedDB используется совместимый localStorage fallback.

Административная сводка здоровья продукта теперь также возвращает
`X-Request-ID` и фиксирует безопасный статусный event. Это связывает проблемы
в консоли с серверным ответом без записи метрик и пользовательских данных.

Checkout и Stripe webhook теперь используют такой же сквозной request ID и
события исхода. В журнал попадает только код ответа: подпись Stripe, план,
платёжные идентификаторы и полезная нагрузка webhook не записываются.

Выпуск краткоживущего токена для iPhone bridge получил такой же контракт
наблюдаемости. Он возвращает `X-Request-ID`, а событие фиксирует лишь исход,
никогда не включая токен, сессию или поля профиля.

Чтение личных обращений и пользовательские ответы на них также возвращают
`X-Request-ID` и создают разделённые безопасные события без текста сообщения,
полей заявки и вложений.

Административные переключатели функций и настройки выпуска получили сквозной
`X-Request-ID` на чтении и записи. События хранят только тип операции и код
ответа, поэтому не раскрывают ключи, значения и данные администратора.

Создание обращения и административная очередь поддержки теперь тоже возвращают
сквозной `X-Request-ID` для GET, PATCH и POST. Логи содержат только направление
операции и HTTP-статус, без текста, вложений и диагностических полей заявки.

Удаление аккаунта и ответ о восстановлении через повторный OAuth-вход теперь
также коррелируются через `X-Request-ID`. В событиях остаётся лишь код ответа,
без идентификатора, причины удаления, сессии и данных профиля.

Выход из текущей сессии и отзыв всех сессий возвращают `X-Request-ID` с теми
же безопасными событиями исхода. В журнал не попадают cookie, session ID и
идентификатор пользователя.

Проверка и активация beta-приглашений также получили сквозной `X-Request-ID`.
Журналируетcя только статус операции: код приглашения, заметка и данные
пользователя не попадают в событие.

Чтение личных обращений выделено в server use case. В нём сосредоточены
владельческая выборка, безопасное представление сообщений и URL вложений; HTTP
маршрут оставляет аутентификацию, параметры запроса и транспортный ответ.

Экспорт персональных данных возвращает `X-Request-ID` и безопасное событие
исхода. Содержимое выгрузки, данные профиля и идентификатор пользователя не
попадают в журнал.

Сбор пользовательской выгрузки вынесен в server use case. Он централизует
выборки D1 и исключение внутренних ключей вложений, учётных данных push и
административных полей; HTTP-маршрут сохраняет проверку доступа и заголовки
файла.

Список пользователей в административной панели теперь использует отдельный
read use case для валидации фильтров, пагинации, D1-запросов и безопасной
проекции profile JSON. Маршрут отвечает за проверку прав и HTTP-ответ.

Административные приглашения вынесены в server use case: ограничение списка,
пакетное создание, условный отзыв и audit event выполняются вне HTTP-маршрута.
Все три ответа также коррелируются через `X-Request-ID` без кодов приглашений
и заметок в журнале.

Проверка достижений вынесена в server use case: доверенный контекст строится
из profile JSON, клиентский контекст ограничивается разрешёнными полями, а
идемпотентная запись новых достижений выполняется отдельно от HTTP-маршрута.

Чтение достижений также стало отдельным use case: D1-строки и снимки состояний
нормализуются до передачи в HTTP-ответ, а маршрут отвечает за feature flag,
аутентификацию и наблюдаемость.

Push-статус, подписка, отписка и тестовая доставка теперь возвращают
`X-Request-ID` и пишут безопасные события исхода. В логи не попадают endpoint,
ключи подписки, данные уведомления и идентификатор пользователя.

Синхронизация данных wearable bridge и Huawei Health также возвращает
`X-Request-ID`. События содержат только исход HTTP-операции, никогда не
включая измерения здоровья, OAuth-токены или сведения о пользователе.

Выдача вложений поддержки теперь тоже сохраняет сквозной `X-Request-ID`.
Событие фиксирует лишь HTTP-статус и не содержит идентификаторов заявки,
пользователя, файла или данных вложения.

CSV-выгрузка личного списка покупок вынесена в server use case: проверка
недели, агрегация ингредиентов и безопасное экранирование CSV тестируются вне
HTTP-маршрута. Скачивание возвращает `X-Request-ID` без содержимого списка в
журнале.

Журнал административных действий получил отдельный read/export use case:
параметры поиска и пагинации нормализуются до D1-запроса, а CSV формируется и
экранируется отдельно от проверки прав. Оба варианта ответа возвращают
`X-Request-ID`; событие содержит только результат HTTP-операции без данных
аудита, фильтров и содержимого файла.

Отчёт по стоимости AI вынесен в отдельный read use case с воспроизводимым
расчётом дневного и недельного периода. Маршрут оставляет проверку
администратора и возвращает `X-Request-ID`; телеметрия фиксирует только статус
ответа, без email и показателей пользователей.

Административная карточка пользователя теперь возвращает `X-Request-ID` для
диагностики. Событие результата содержит только статус HTTP-ответа: данные
профиля, сессий, подписки и самого пользователя в журнал не попадают.

Журнал AI-вызовов получил отдельный read use case: лимит и фильтры
нормализуются до построения параметризованного D1-запроса. Маршрут сохраняет
проверку администратора и добавляет `X-Request-ID`; в событие не попадают
параметры фильтра, user ID и тексты ошибок модели.
