# Архитектурная переработка FitFocus

Документ фиксирует порядок безопасной переработки без «большого взрыва». Каждая
итерация должна оставлять приложение запускаемым, сопровождаться тестами и
выходить отдельным pull request.

## Принципы

- Сохранять действующие API, ключи browser storage и D1-схему, пока потребитель
  не переведён на новую границу.
- Делать локальную запись перед фоновой синхронизацией с облаком.
- Не переносить бизнес-правила в React-экраны или HTTP routes.
- Измерять ошибки, задержки и конфликты до и после изменения.

## Очередь работ

1. **Границы фронтенда.** Вынести profile, diary, AI и family в feature-модули;
   оставить в `App.tsx` shell, сессию и навигацию.
2. **Хранилище.** Перевести данные дневника, истории и настроек на typed
   repositories с сохранением текущего формата ключей. Затем перенести объёмные
   данные в IndexedDB и добавить надёжную outbox-очередь.
3. **Серверные use cases.** Сделать Pages routes HTTP-адаптерами, а правила
   профиля, семейного доступа, квот и платежей перенести в application/domain.
4. **Надёжность внешних интеграций.** Ввести единый HTTP-клиент с timeout,
   классификацией ошибок и безопасными ограниченными повторами.
5. **Наблюдаемость.** Добавить request ID, структурированные события,
   dashboard/alerts для API, синхронизации, AI и платежей.
6. **Данные и выпуск.** Нормализовать критичные части profile JSON, расширить
   контрактные и мобильные smoke-тесты, выпускать изменения под feature flags.

## Первый срез

В этом изменении вводятся `UserStateRepository` и `useProfilePersistence`.
Репозиторий уже обслуживает дневник, историю, настройки, избранные рецепты и
последний AI-совет. `features/diary` обслуживает выбор дня, итоги и действия с
записями и историей. Операции семьи сведены в `features/family/familyApi.ts`,
а подготовка данных AI-советника — в `features/ai`. UI-хуки управляют только
состоянием и сценариями экрана. Все новые границы используют существующие
ключи `fitfocus_data_<user>_*` и текущий механизм синхронизации, поэтому не
требуют миграции пользовательских данных.

Репозиторий пользовательских данных теперь связывает каждый ключ с типом
значения при записи. Некорректные данные не попадают в локальное хранилище и
очередь фоновой синхронизации из-за ошибки в вызывающем коде.

Очередь фоновой синхронизации хранится в browser storage до успешного ответа
сервера. После перезагрузки она возобновляется, когда пользовательская сессия
готова; изменения одного ключа по-прежнему объединяются в последнюю операцию.

Семейный API использует общий browser HTTP-клиент: GET-запросы имеют тайм-аут
и один ограниченный повтор при временной ошибке. Изменяющие запросы не
повторяются автоматически, чтобы избежать повторной записи на сервере.

Проверка запросов синхронизации вынесена из `/api/state` в server use case.
Маршрут остаётся HTTP-адаптером, а правила формата, версии и допустимого
пространства ключей тестируются отдельно от D1.

Атомарная запись и удаление состояния также вынесены в слой D1 use case;
маршрут не содержит SQL-правил сравнения версий и обработки конфликтов.

Чтение синхронизируемого состояния вынесено в общий use case для `/api/state`
и bootstrap; оба сценария фильтруют запрещённые ключи, включая старые
локальные снимки `_all_users`.

Команды изменения профиля используют отдельный server use case: он фильтрует
поля клиента, сохраняет защиту keyspace, проверяет версию, определяет план на
сервере и выполняет CAS-запись. PUT и PATCH остаются HTTP-адаптерами.

Загрузка профиля вынесена в общий read use case для `/api/profile` и
`/api/bootstrap`; идентификатор, тариф и миграция прежней учётной записи
вычисляются одинаково во всех сценариях входа.

Синхронизация состояния получает сквозной `X-Request-ID`: браузер добавляет
его к запросу, сервер возвращает в ответе и пишет компактное структурированное
событие с кодом результата без тел запросов и идентификатора пользователя.

Синхронизация профиля использует тот же browser HTTP-клиент: для каждого
запроса добавляется `X-Request-ID`, действует единый тайм-аут, а профильный
маршрут возвращает идентификатор и пишет структурированное событие ответа.

Стартовый запрос bootstrap использует безопасный повторяемый GET-транспорт и
передаёт `X-Request-ID`; сервер возвращает идентификатор и фиксирует исход
гидратации без данных пользователя.

Еженедельные AI-отчёты теперь также используют `UserStateRepository`: формат
ключа и данных сохранён, а записи проходят через локальное сохранение и
долговечную очередь фоновой синхронизации.

Сценарий AI-совета вынесен из `App.tsx` в feature-хук: проверка тарифа,
формирование контекста, запись результата, учёт использования и проверка
достижения выполняются как единый тестируемый use case. Экран сохраняет только
состояние отображения карточки и индикатора загрузки.

Проверка сессии и кода приглашения в браузере также используют общий HTTP
транспорт: безопасное чтение имеет ограниченный повтор, а изменяющая POST-
проверка не повторяется автоматически, но получает тайм-аут и request ID.

Обработка фото еды вынесена в AI feature: сжатие, анализ, локальная запись
дневника, отображение результата и учёт использования тестируются отдельно от
экрана. Пакет изображений ограничивается оставшимся дневным лимитом, поэтому
массовая загрузка не может его обойти. Неизвестный или повреждённый тариф
обрабатывается как отсутствие доступных сканирований.

Генерация личного недельного меню стала отдельным AI-сценарием: feature
управляет индикатором, понятной ошибкой, сохранением обновлённого профиля и
сигналом достижения. Экран плана получает готовый обработчик и состояние.

Контекст недельного AI-отчёта строится одним feature-builder для фоновой
генерации и ручного повтора. Это исключает расхождение данных между путями.

Ошибка сжатия или анализа одного фото записывается отдельно и не отменяет
обработку остальных файлов выбранного пакета.

Повтор AI-действий вынесен в use case с независимыми проверками для совета,
плана, объяснения плато и недельного отчёта. Действие из устаревшей записи
другого пользователя больше не запускается в текущей сессии.

Фоновая генерация недельного AI-отчёта теперь выполняется в feature-хуке:
дедупликация, сохранение последнего действия, обновление отчётов и обработка
ожидаемых ошибок не остаются в корневом экране.

Сброс дневных и недельных квот вынесен в чистый usage-сценарий. Он использует
общие календарные ключи вместо форматирования даты через локаль браузера.
