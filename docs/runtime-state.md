## Что подключено

Дополнение `dac2de2`: [bootstrap/state-hydration](bootstrap-hydration.md)
проверяют свежий `/me` proof и scope ответа; применение managed state и seed
профиля проверяет epoch/auth-fence той же транзакцией. Повторное чтение
идентичного owned-снимка не увеличивает revision. Новая версия всё равно
защищает независимого редактора. Результаты дополнения отделены от
исторического контракта шести ключей ниже.

[UserStateRepository](../storage/userStateRepository.ts) используется приложением
для diary, history, favorite_recipes, weekly_reports, last_coach_card и settings.
Для этих шести ключей value, локальная ревизия и отдельная операция outbox
коммитятся одной IDB-транзакцией. Сначала значение, затем отдельная постановка
в Map больше не используются этим repository. Delete удаляет value и сохраняет
delete-intent; новое значение и delete не отменяют существование друг друга.

Методы writeJson/remove возвращают Promise результата commit. Quota/abort или
недоступная IDB дают отказ; запасная localStorage-outbox не создаётся.
Прежний localStorage value удаляется только после принятой транзакционной правки.
Оставшаяся копия не оживляет подтверждённое локальное удаление.

## Редактор, причинность и конфликты

Repository запоминает ревизию прочитанного снимка. Запись не получает свежую
ревизию другой вкладки непосредственно перед commit. Независимая устаревшая
правка сохраняется отдельной conflicted-операцией, не затирая values.
Продолжение того же редактора связывается явным parentOpId.

Если parent ещё pending/sending, новая операция использует его фактическую базу
внутри транзакции. Если точный parent уже подтверждён, key metadata проверяет
его opId/writerId/revision перед использованием подтверждённой версии.
Подтверждение чужой правки не разрешает такое продолжение.

Вход передаёт UI тот же repository, который прочитал значения при hydration;
создание нового редактора после чтения не подменяет его наблюдавшуюся ревизию.
Позднее завершение прежнего входа не заменяет UI после logout/нового входа.
Глобальная координация авторизации и поздних HTTP-ответов пока остаётся задачей.

## Загрузка из облака и настройки

[Hydration](../sessionHydration.ts) запрашивает includeDeleted=1. Для шести ключей
облачное значение или отсутствие применяется только при protocol 2, корректном
полном списке и безопасной версии. Применение проверяет локальную ревизию,
владельца, отсутствие любых pending/sending/conflicted/failed по ключу и
неуменьшение подтверждённой версии в одной IDB-транзакции.

Необработанный legacy-источник и прежние локальные значения не считаются
доказанной серверной генерацией. Их загрузка не разрешает перезаписать локальное
намерение. Проверка localStorage не заменяет реальную остановку старых writers.
Старые raw-IDB write/remove не могут изменять ключ с durable-владельцем.

Настройки читаются асинхронно из IDB. Загрузка не записывает настройки по умолчанию
и не пишет нормализованный список рецептов поверх неподтверждённого содержимого.
Недельный отчёт использует один редактор для чтения/записи и ожидает commit;
конфликт или ошибка хранения не возвращается как успешное сохранение отчёта.

## Что видит пользователь

[StateStorageNotice](../ui/StateStorageNotice.tsx) показывает отказ сохранения,
конфликт, blocked и ожидание синхронизации также на мобильном экране.
Ошибка доступна также ожидающему Promise вызывающему коду;
игнорирование Promise в обработчике UI не создаёт необработанное исключение.
Содержимое пользовательских данных не выводится в сообщении или журнале статуса.

Индикатор облака учитывает известную очередь аккаунта: pending/sending не выглядят
как saved, а ошибка хранения/conflicted/failed имеет приоритет над успехом profile.
Перезагрузка читает состояния очереди; отдельная успешная запись не скрывает
сохранённый конфликт другого изменения. Этот индикатор ещё не является общей
проверкой всех legacy/profile writers и вкладок.

### Повтор и разрешение конфликтов — рабочее дерево, 13.10.2026

Панель показывает операции по разделам, используя безопасные названия и статус;
значения, содержимое профиля и сырые payload в интерфейсе не выводятся.

- **Повторить отправку** доступно для обычных `failed`-операций после свежей
  проверки сессии. В транзакции сверяется точный набор operation IDs. Исходное
  значение и порядок сохраняются; failed-попытка возвращается в `pending` с новой
  ограниченной retry-серией.
- **Отправить последнюю локальную версию** сводит операции одного ключа к
  последнему сохранённому намерению. Требуются свежий read guard, неизменившийся
  набор операций и отсутствие `sending`/legacy evidence. Для серверного
  version-конфликта используется только проверенный серверный снимок и его
  версия. Замена значения и outbox выполняется одной транзакцией.
- **Принять серверную версию** применяет проверенный снимок, очищает локальные
  варианты и обновляет подтверждённую версию атомарно. Перед действием UI
  предупреждает о потере локальной правки; после применения страница
  перезагружается, чтобы перечитать профиль и данные из общей базы.

Legacy-записи с migration provenance сохраняются, но ручной retry и
разрешение через эту панель для них отключены. Если ответ 409 не содержит корректного
scope и снимка, sender ставится на `protocol`-паузу; такой ответ не становится
разрешаемым конфликтом. Устаревшие operation IDs, смена auth-fence/сессии и
операция в `sending` отклоняют действие без изменения очереди.

Проверенные числа и ограничения: [журнал](stabilization-progress.md).
Fake-IDB quota и внесённый браузерный отказ не доказывают реальное заполнение диска.
Следующий после этого снимка этап sender на claim/finish, подтверждённой
auth-сессии и HTTP-исходов описан в [state sender](state-sender.md).
Остаются остальные writers/profile и их полный lifecycle; legacy evidence требует
отдельной политики, а разрешение сервера/повтор требуют широкой приёмки для
остальных ресурсов и ошибок. Прежний hybrid sender ещё активен для оставшихся
путей; эту промежуточную ветку нельзя считать готовой к выпуску.

Прежний raw-импорт backup не может перезаписать durable-owned value. Такой отказ
теперь возвращается как ошибка, а не успех восстановления. Полноценный экспорт
и атомарное восстановление очереди/карантина пока не реализованы; существующий
импорт нескольких хранилищ не следует считать общей атомарной транзакцией.

## Последующее персональное меню

На [`f4b4eee`](https://github.com/Michael-edel/FitFocus/commit/f4b4eee1e577292019481b711b097941df27558e) generated profile использует эту же IDB-outbox с дополнительным
транзакционным readGuard и lifetime predicate. Меню публикуется после commit;
независимые edits, logout и поздние ответы проверяются отдельно от sender.
[Контракт](ai-session-guard.md), [профиль](profile-persistence.md#сохранение-сгенерированного-результата).
Личные покупки теперь входят в одну durable profile-операцию и обновляют
SQL-проекцию только при принятом profile CAS
([контракт](personal-menu-projection.md)). Семейное меню и списки покупок
используют отдельную `familyMenu` outbox-операцию с CAS по семье и неделе
([контракт](family-menu-state.md)). Эти пути имеют собственные гарантии версии
и порядка; другие AI/retry/family callbacks, runtime legacy lifecycle,
конфликты, экспорт/очистка и выпуск всё ещё требуют приёмки.
Историческое описание `cfcc31b` выше сохраняется как снимок своей реализации.

## Последующее подключение runtime legacy

В текущем follow-up [legacy importer](legacy-migration.md) запускается после
свежего `/api/me`. Он сопоставляет только записи точного аккаунт-префикса и
открывает отправку лишь после ответа Service Worker и всех вкладок текущим
build id. Источник сохраняется; неответившая или старая вкладка закрывает gate.
Actual old/new bundle migration с сохранённым pending intent проверен в
[browser smoke](legacy-migration.md#browser-acceptance--13102026) на семи проектах.

## Последующее расширение JSON backup — 13.10.2026

Текущий backup v3 читает все пять долговечных stores одним readonly-снимком и
восстанавливает отсутствующие values, operations, migration ledger, quarantine
и durable meta одной readwrite-транзакцией. Конфликт существующего primary key
откатывает всю IDB-часть; точный повтор файла идемпотентен. v1/v2 по-прежнему
импортируются, но не содержат outbox и migration records.

`active-session`/`auth-fence` не входят в переносимую копию. При восстановлении
legacy progress переводится в `partial` с закрытым `sendAllowed`; runtime обязан
заново проверить исходный ключ и текущий all-client Service Worker fence.
localStorage восстанавливается отдельно с возвратом прежних значений при
ошибке, поскольку общей транзакции с IndexedDB нет.
[Контракт, проверки и ограничения](backup-restore.md). Базовые действия recovery
добавлены в UI; остаются их широкая lifecycle-приёмка и остальные callbacks.
