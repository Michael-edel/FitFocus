# P0.8: подключение пользовательских данных к outbox

Обновлено: 09.10.2026. Ветка fix/durable-outbox, [draft PR #93](https://github.com/Michael-edel/FitFocus/pull/93).
Серверная зависимость — [PR #94](https://github.com/Michael-edel/FitFocus/pull/94),
объединённая коммитом 93f90c0. Это промежуточная реализация;
HTTP sender, авторизация, все writers и выпуск ещё не завершены.

## Что подключено

[UserStateRepository](../storage/userStateRepository.ts) используется приложением
для diary, history, favorite_recipes, weekly_reports, last_coach_card и settings.
Для этих шести ключей value, локальная ревизия и отдельная операция outbox
коммитятся одной IDB-транзакцией. Сначала значение, затем отдельная постановка
в Map больше не используются этим repository. Delete удаляет value и сохраняет
delete-intent; новое значение и delete не отменяют существование друг друга.

Методы writeJson/remove возвращают Promise результата commit. Quota/abort или
недоступная IDB дают отказ; запасная localStorage-outbox не создаётся.
Прежний localStorage value удаляется только после принятой транзакционной правки.
Оставшаяся копия не оживляет подтверждённое локальное удаление.

## Редактор, причинность и конфликты

Repository запоминает ревизию прочитанного снимка. Запись не получает свежую
ревизию другой вкладки непосредственно перед commit. Независимая устаревшая
правка сохраняется отдельной conflicted-операцией, не затирая values.
Продолжение того же редактора связывается явным parentOpId.

Если parent ещё pending/sending, новая операция использует его фактическую базу
внутри транзакции. Если точный parent уже подтверждён, key metadata проверяет
его opId/writerId/revision перед использованием подтверждённой версии.
Подтверждение чужой правки не разрешает такое продолжение.

Вход передаёт UI тот же repository, который прочитал значения при hydration;
создание нового редактора после чтения не подменяет его наблюдавшуюся ревизию.
Позднее завершение прежнего входа не заменяет UI после logout/нового входа.
Глобальная координация авторизации и поздних HTTP-ответов пока остаётся задачей.

## Загрузка из облака и настройки

[Hydration](../sessionHydration.ts) запрашивает includeDeleted=1. Для шести ключей
облачное значение или отсутствие применяется только при protocol 2, корректном
полном списке и безопасной версии. Применение проверяет локальную ревизию,
владельца, отсутствие любых pending/sending/conflicted/failed по ключу и
неуменьшение подтверждённой версии в одной IDB-транзакции.

Необработанный legacy-источник и прежние локальные значения не считаются
доказанной серверной генерацией. Их загрузка не разрешает перезаписать локальное
намерение. Проверка localStorage не заменяет реальную остановку старых writers.
Старые raw-IDB write/remove не могут изменять ключ с durable-владельцем.

Настройки читаются асинхронно из IDB. Загрузка не записывает настройки по умолчанию
и не пишет нормализованный список рецептов поверх неподтверждённого содержимого.
Недельный отчёт использует один редактор для чтения/записи и ожидает commit;
конфликт или ошибка хранения не возвращается как успешное сохранение отчёта.

## Что видит пользователь

[StateStorageNotice](../ui/StateStorageNotice.tsx) показывает отказ сохранения,
конфликт, blocked и ожидание синхронизации также на мобильном экране.
Ошибка доступна также ожидающему Promise вызывающему коду;
игнорирование Promise в обработчике UI не создаёт необработанное исключение.
Содержимое пользовательских данных не выводится в сообщении или журнале статуса.

Индикатор облака учитывает известную очередь аккаунта: pending/sending не выглядят
как saved, а ошибка хранения/conflicted/failed имеет приоритет над успехом profile.
Перезагрузка читает состояния очереди; отдельная успешная запись не скрывает
сохранённый конфликт другого изменения. Этот индикатор ещё не является общей
проверкой всех legacy/profile writers и вкладок.

## Проверки и дальнейшая работа

- [Repository](../tests/user_state_repository_indexed.test.ts): commit/reload,
  цепочки put/delete, разные редакторы, quota/rollback/retry, подтверждённый parent,
  settings, защита от raw-writer и поздней hydration.
- [Hydration](../tests/session_hydration_durable.test.ts): protocol 2, pending
  и delete, tombstone/recreate, испорченный ответ, legacy и запись во время HTTP.
- [Браузер](../e2e/storage-durability.spec.ts): изменение темы, reload с outbox,
  внесённый quota-отказ и явная ошибка без ложного Cloud: saved.

Проверенные числа и ограничения: [журнал](stabilization-progress.md).
Fake-IDB quota и внесённый браузерный отказ не доказывают реальное заполнение диска.
Следующий шаг — sender на claim/finish, подтверждённая auth-сессия и HTTP-исходы.
Остаются остальные writers/profile, runtime legacy-импорт с реальным барьером,
экспорт/очистка новых stores, разрешение конфликтов/повтор в UI и старый/новый
bundle на одном origin. Прежний hybrid sender ещё активен для оставшихся путей;
эту промежуточную ветку нельзя считать готовой к выпуску.

Прежний raw-импорт backup не может перезаписать durable-owned value. Такой отказ
теперь возвращается как ошибка, а не успех восстановления. Полноценный экспорт
и атомарное восстановление очереди/карантина пока не реализованы; существующий
импорт нескольких хранилищ не следует считать общей атомарной транзакцией.
