# Синхронизация FitFocus

Снимок: 09.10.2026, `810adb1`. [Область документации](README.md).

Последующее подключение в PR #93: [runtime state](runtime-state.md).
Шесть ключей repository пишутся атомарно с IDB-outbox, managed hydration
защищает локальное намерение и читает protocol 2. HTTP sender и другие writers
пока используют прежние пути; риски исходного снимка ниже не считаются
исправленными для всего приложения.

## Что делает текущий код

`hybrid.ts` держит одну операцию на ключ в Map, один раз загружает очередь
из `fitfocus.remote-kv-outbox.v1` и сохраняет Map целиком в localStorage.
Задержка отправки — 400 ms, повтор — фиксированные 2 s, auth-пауза — 30 s.
Это не транзакционная очередь и не exponential backoff.

Известные опасные пути:

- 409 может удалить исходящую операцию или заменить локальный снимок;
- при auth-паузе новая локальная запись может не попасть в очередь;
- две вкладки могут перезаписать очереди друг друга даже для разных ключей;
- версия и применение ответа защищены не всеми проверками, которыми
  защищено удаление старого объекта из Map;
- hydration и profileSync способны применить облачный снимок поверх
  неподтверждённых локальных изменений;
- физическое удаление `user_kv` допускает повторное использование версии.

Профиль имеет отдельную Promise-цепочку; `storage/outbox.ts` содержит другой
scaffold-формат. Ни один из них нельзя молча считать общей новой очередью.

## Требуемое поведение — ещё не реализовано

Серверный компонент [P0.7](state-generations.md) в `fix/state-generations`
сохраняет поколение после delete и возвращает собственную версию мутации.
Это отдельное последующее изменение к снимку выше. Клиент ещё должен читать
tombstones, сохранять 409-intent, получать подтверждённую DELETE-версию
и отдельно разрешать старые операции без доказательства серверного поколения.
Нельзя выводить из серверных тестов, что runtime-очередь уже исправлена.

Единственный источник очереди — IndexedDB, независимо от Web Locks.
Состояния: `pending` → `sending` → подтверждение с удалением/архивированием;
либо `pending` для повтора, `conflicted` для разрешения конфликта,
`failed` для неповторяемой ошибки. Пауза авторизации не запрещает новые записи.

| Результат отправки | Действие нового клиента |
|---|---|
| Подтверждённый успех | Применить только к соответствующей операции/попытке |
| 409 | Сохранить локальный payload, delete-intent и доступный server snapshot |
| 401 | Приостановить отправку; локальные изменения сохранять |
| 403 | Разобрать ACCESS_REQUIRED/FORBIDDEN_KEYSPACE, показать причину |
| 408/429/5xx, сетевой сбой | Повтор с ограниченной задержкой/backoff и учётом Retry-After, где применимо |
| Остальные неповторяемые 4xx | Сохранить как failed с причиной |
| 404 | Успех только если конкретный endpoint явно гарантирует идемпотентное отсутствие |

Точная политика числа повторов и верхней задержки фиксируется с реализацией;
бесконечный быстрый retry недопустим. Lost response после серверного commit
может дать 409 при повторе: нельзя удалять операцию без проверки подтверждения.
Серверная идемпотентность добавляется там, где CAS и проверяемого состояния
недостаточно; сам client opId не делает API идемпотентным.

## Порядок, владение и поздний ответ

Claim операции и переход в sending выполняются IDB-транзакцией. В ней
фиксируются accountId, opId, локальная ревизия, attemptId, sessionEpoch,
owner и startedAtMs. HTTP начинается только после commit.
Завершение проверяет эти значения и меняет состояние/версию транзакционно.
Просроченный lease восстанавливается новой попыткой; старый ответ игнорируется.

Если правка B продолжает локальную правку A того же автора, связь должна
быть записана явно. Тогда подтверждение A может дать B новую базу по этому
правилу. Независимые полные снимки из разных вкладок автоматически не
перебазируются: это скрывало бы потерю одной из правок.

Новая сессия того же accountId может возобновить сохранённую очередь;
чужой accountId не получает к ней права. Ответ старой сессии не применяется
после смены аккаунта. Перед cloud hydration проверяются локальная ревизия
и незавершённые операции; свежий snapshot сам по себе не разрешает конфликт.

## Миграция и недоступность хранилища

В PR #93 реализован отдельный компонент LegacyQueueMigration. Порция,
ledger и прогресс коммитятся вместе; claim/finish импортированной операции
проверяют разрешение отправки и соответствующий migration item. Подтверждение
отправки сохраняется атомарно с удалением операции, предотвращая повторный
импорт после ack. Прежние снимки источника учитываются после прерывания.
Компонент ещё не вызван из работающего приложения; подтверждённые owners
и остановку старых writers должна обеспечить интеграция.
[Подробный контракт](legacy-migration.md).

Legacy-ключ — только источник импорта. Нормализация, fingerprint, карантин,
транзакции и совместимость вкладок описаны в [ADR-005](adr/ADR-005-durable-outbox.md).
При недоступной IDB не создаётся вторая авторитетная очередь в localStorage.
Пользователь получает явное состояние «не сохранено» и возможность повторить
или сохранить доступные данные. Успех IDB означает завершённую транзакцию;
абсолютная гарантия при физической потере устройства не обещается.

## Матрица приёмки

| Сценарий | Что должно остаться после проверки |
|---|---|
| Offline → запись → reload → online | Данные и намерение сохранены, отправка возобновилась |
| Abort/quota во время записи | Нет половины «данные без операции»; показана ошибка |
| 409 update/delete → reload | Локальная правка/удаление и конфликт доступны |
| 401 → новая правка → login | Новая операция сохранена и отправлена своим аккаунтом |
| 403 access/keyspace | Понятная причина, операция не потеряна |
| Cloud hydration при pending | Локальный снимок не затёрт |
| A отправляется, B записывается, приходит A | B не удалена и не подтверждена ошибочно |
| Account A → B во время HTTP | Ответ A не меняет B; очередь A не отправлена как B |
| Две вкладки, разные ключи, без Web Locks | Обе операции сохранены |
| Две вкладки, один полный JSON-снимок | Сохранён конфликт, правки не скрыто перезаписаны |
| Отправляющая вкладка закрылась | Lease истёк, новая попытка допустима, старый ответ безопасен |
| Сервер commit, ответ потерян | Повтор не теряет намерение и не подтверждает чужую версию |
| Legacy повтор/перестановка/retryCount | Нет дубликатов из-за индекса/числа повторов |
| Legacy abort между импортом и отметкой | Вся порция откатилась и повторяется |
| Повреждённая/неизвестная legacy | Raw сохранён, auto-send запрещён, статус partial |
| Старый и новый build на одном origin | Blocked/закрытие соединений проверены фактически |
| Delete → recreate → stale update | Старая версия не проходит CAS |

Unit и fake IndexedDB проверяют логику и отказные пути. Два реальных
browser page нужны для вкладок; старый и новый bundle — для совместимости.
Mock API не заменяет staging D1/OAuth/push. Результаты связываются с SHA
в [TASKS](../TASKS.md) и [чек-листе](../RELEASE_CHECKLIST.md).
