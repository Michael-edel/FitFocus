# Подготовка выпуска проекции личных покупок

Сверено: 12.10.2026. Этот документ описывает промежуточную серверную версию,
последовательность перехода и проверенную границу. Общие условия выпуска —
в [RELEASE_CHECKLIST](../RELEASE_CHECKLIST.md). Staging и production ещё не пройдены.

## Версии и назначение

| Версия | Назначение |
|---|---|
| База `14ca6380b6bb5bd918c5c71c68b0ca68a5ffb5d5` | Последняя ревизия перед новой проекцией; схема до 0019 |
| Подготовительный код `dde4c7132a0a810f8c358c5935b084ff31e2cb43`, ветка `fix/profile-cas-rollout` | Подтверждение profile CAS через `RETURNING`; прежнее чтение и запись покупок |
| Итоговая проекция `2d1f480a71b4c8d6cb90e90e1308074a08082371`, ветка `fix/durable-outbox` | Проекция принятого profile, новая capability, отказ отдельного личного POST и валидация меню |

Подготовительная ветка намеренно создана от `14ca638`, поскольку полный
сервер проекции уже требует новую таблицу. Это зависимая промежуточная
версия для выпуска; её нельзя целиком сливать поверх более новой ветки.
[Diff подготовительного кода](https://github.com/Michael-edel/FitFocus/compare/14ca6380b6bb5bd918c5c71c68b0ca68a5ffb5d5...dde4c7132a0a810f8c358c5935b084ff31e2cb43)
содержит пять файлов: profile CAS, SQLite D1 helper и три связанных теста.
Клиент, зависимости, схема и миграции этой поправкой не изменены.

`D1 meta.changes` учитывает записи SQL triggers. Проверка `changes === 1`
после их установки может сообщить конфликт после успешного сохранения.
Оба варианта profile CAS теперь получают `RETURNING version` и подтверждают
строку своей условной мутации. Отсутствующая строка остаётся конфликтом.

## Порядок перехода

1. Проверить исходную среду, резервную копию, точные SHA артефактов и CI.
   Развёртывать подготовительные серверные функции на БД до 0019.
   Подтвердить создание и обновление profile, прежние POST/read покупок.
2. При работающем подготовительном сервере применить миграцию
   `0020_personal_menu_projections.sql`. Сохранить legacy-строки и проверить
   таблицу `personal_menu_projections`, оба triggers и метаданные миграции.
   Подтвердить, что profile CAS возвращает успех после записи trigger.
3. Развёртывать сервер проекции. Проверить
   `profileSync.weeklyMenuProjection = 1` в `/api/me`, profile CAS,
   покупки/CSV, пустое меню и отказ прежнего личного items POST.
4. После серверного smoke включать новый клиент. До появления capability
   он сохраняет локальное намерение с protocol-паузой; старый read-контракт
   отдельно допускает clean refresh.
5. На staging пройти реальные старый/новый bundles, сессии, два аккаунта,
   reload и повтор pending-операции. Только после этого принимать выпуск.

Нельзя сначала применять 0020 поверх прежнего CAS с `changes === 1`.
Полный сервер проекции также нельзя запускать до 0020. Промежуточный
сервер не объявляет новую capability даже после установки таблицы.
Порядок относится к серверным функциям; новый клиент включается на шаге 4.

## Проверка перехода на одной локальной БД

Workerd/D1, синтетический аккаунт, один origin `127.0.0.1:8798`, одна
изолированная БД и сессия. Серверный артефакт менялся без пересоздания БД;
миграция 0020 применялась при работающем подготовительном сервере.
Выполнены 30 HTTP-запросов, включая проверки готовности после смены версии.

| Этап | Наблюдавшийся результат |
|---|---|
| 0019 + подготовительный сервер | Profile CAS: 200/version 1; прежние POST/read покупок работают; новой capability нет |
| 0020 + тот же сервер | CAS: 200/version 2 при записи trigger; прежний POST сохраняется и читается прежним reader |
| Включение сервера проекции | Capability появилась; покупки показывают канонические 300 г вместо legacy 999 г |
| Прежний личный POST | 409 `PERSONAL_MENU_PROFILE_REQUIRED`; принятые покупки не меняются |
| Пустой снимок | CAS: version 3; список пуст, legacy не восстанавливается |
| Последовательность прежнего клиента | PUT принят с version 4 и 400 г; следующий items POST получает 409, покупки остаются 400 г |
| Некорректное меню / неверная сессия | Соответственно 422 / 401; версия остаётся 4 |
| Негативный откат reader | Подготовительный reader показывает устаревшие 999 г при сохранённом profile version 4 |
| Возврат сервера проекции | Снова читаются принятые 400 г; данные не удалялись |

SHA-256 применённой миграции:
`a403d46a8d55eae4e4ff8934308d831377afd18d0f12a7a86b3ee8ce55028c91`.
Локальные свидетельства: `projection-staged-rollout-smoke.log`,
`rollout-0020-migration.log`, `profile-cas-rollout-unit.log`,
`profile-cas-rollout-gates.log` и `profile-cas-rollout-build.log`.
Они хранятся вне Git; таблица выше фиксирует результаты для указанных SHA.

Это проверка настоящего локального HTTP/SQLite-пути. Последовательность
запросов прежнего клиента не заменяет запуск прежнего bundle в браузере,
проверку production D1 или staging.

## Откат и оставшиеся критерии

После принятия канонических покупок откат функций к прежнему reader
неприемлем: локальная проверка воспроизвела показ устаревшего списка.
При откате клиента сервер должен продолжать читать каноническую проекцию.
Возврат функций требует отдельно проверенного совместимого артефакта.
Таблицы проекции, legacy-строки и pending-операции сохраняются.

- [x] Подготовить отдельную версию CAS и проверить локальный переход 0019 → 0020.
- [x] Воспроизвести опасный откат reader и восстановление канонического чтения.
- [ ] Подтвердить CI опубликованного подготовительного HEAD.
- [ ] Пройти тот же переход, реальные bundles и совместимый откат на staging.
- [ ] Проверить release SHA и интеграцию через защищённую main.

Семейные writers, runtime legacy-импорт, UI конфликтов и backup/очистка
всех stores остаются в [TASKS](../TASKS.md); этот компонент их не закрывает.
