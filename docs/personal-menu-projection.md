# Личное меню и список покупок: текущая переработка

Сверено: 12.10.2026. Статус: незакоммиченная реализация на базе
[`42ee434`](https://github.com/Michael-edel/FitFocus/commit/42ee4348113e94d43cb24d6950ccd1bd7be597bc).
Общий план — [TASKS](../TASKS.md), подтверждённая область —
[матрица проверок](verification-matrix.md). Этот документ не объявляет
новый контракт выпущенным или полностью принятым.

## Проблема опубликованного кода

На `42ee434` личное меню сначала сохраняется в IDB вместе с profile-операцией,
затем клиент отдельно вызывает `POST /api/weekly_menu/items`.
Между этими действиями возможны reload, завершение вкладки и ошибка сети.
Второй запрос не является постоянной операцией; его session guard не задаёт
CAS и не связывает список покупок с принятой сервером версией profile.
Поздний запрос может заменить более свежий список.
[Контракт этого этапа](ai-session-guard.md) сохраняет прежнюю границу.

## Устройство рабочего варианта

Личное меню и `shoppingListItems` остаются частью profile. Существующая
IDB-outbox доставляет единственную profile-операцию с её владельцем,
baseVersion и защитой попытки. Новая клиентская очередь не вводится.

Миграция `migrations/0020_personal_menu_projections.sql` добавляет серверную
таблицу `personal_menu_projections` и два AFTER-trigger на `user_profiles`.
Принятый profile CAS и запись проекции выполняются в одном SQL statement.
Ошибка проекции откатывает запись профиля. Конфликт profile не должен менять
проекцию. Подтверждение CAS использует `RETURNING version`; счётчик изменений
нельзя трактовать как ровно одну строку при наличии trigger-записей.

| Поле проекции | Назначение |
|---|---|
| `user_id`, `week_start` | Владелец и неделя; составной первичный ключ |
| `items_json` | Снимок ингредиентов из принятого profile |
| `profile_version` | Версия именно этого принятого profile |
| `updated_at` | Время сохранения |

Чтение личных покупок и CSV использует проекцию. Legacy `weekly_menu_items`
читается только при отсутствии канонической записи данной недели.
Пустой снимок означает пустой список; повреждённый снимок даёт ошибку,
а не восстановление старых ингредиентов. Смена недели сохраняет историю;
удаление текущего меню записывает пустое поколение его недели.

Рабочий сервер отклоняет прежний личный items POST кодом
`409 PERSONAL_MENU_PROFILE_REQUIRED`. Семейный путь с `familyId` остаётся
отдельным; его CAS, очередь и lifecycle ещё требуется переработать.
Проекции включены в рабочие export/delete аккаунта и privacy coverage.

`/api/me` объявляет `profileSync.weeklyMenuProjection: 1` только при наличии
таблицы и обоих triggers. Новая генерация и отправка profile требуют эту
capability. Обычное безопасное чтение profile должно продолжать работать
по прежним `profileSync.protocol: 1` и `guard: 1`.

## Что фактически проверено

Локальный регрессионный тест до исправления подтвердил рассогласование:
успешный profile CAS оставлял прежние покупки. Отдельный тест подтвердил
ложный отказ CAS, когда SQL trigger увеличивал счётчик изменений.

После поправок выборочно прошли 22 unit-теста в 5 файлах: profile CAS/write,
items endpoint/use case и новый `tests/personal_menu_projection.test.ts`.
Девять проверок проекции используют настоящий SQLite: конкурентный CAS,
откат, пустой снимок, история недель, некорректное меню, повреждение проекции,
capability, экспорт/удаление и соответствие покупок принятому profile.
Это результат рабочего дерева, а не CI опубликованного SHA.

## До завершения компонента

- [ ] Разделить capability чтения profile и capability отправки проекции
  в `StateSync`: сейчас общий флаг необоснованно блокирует clean refresh
  при отсутствии новой capability. Добавить регрессионные проверки.
- [ ] Переписать menu E2E под единственную profile-операцию. В старом файле
  ещё есть импорт удалённого `WEEKLY_MENU_ITEMS_ERROR` и ожидание items POST;
  этот набор пока не подтверждает новую реализацию.
- [ ] Проверить сохранность opId и меню после ошибки profile PUT и reload,
  восстановление отправки, отсутствие личного items POST и отсутствие
  новой capability до AI. Сохранить logout/quota/lifetime-проверки.
- [ ] Пройти полный unit, typecheck, guards, schema/privacy, build и browser
  matrix; проверить миграцию и `RETURNING` на локальном Worker/D1.
- [ ] Зафиксировать проверенный код, обновить API/data/release документы
  и проверить CI точного нового SHA.
- [ ] Пройти staging и совместимость старой/новой сборок перед выпуском.

Порядок выпуска рабочего решения: миграция БД → серверные functions с
проверенной capability → новый клиент. Неверную legacy-форму меню нельзя
«исправлять» угаданной неделей. Не применять destructive backfill и не
удалять старые покупки ради зелёной проверки.

Общие условия [выпуска](../RELEASE_CHECKLIST.md), семейные writers,
runtime legacy и остальной P0 этим компонентом не закрываются.
