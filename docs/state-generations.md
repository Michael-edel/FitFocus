# P0.7: серверные поколения state

Обновлено: 09.10.2026. Реализовано в ветке `fix/state-generations`,
база — PR #90 (`cc880d9`). Выпуск в main/staging/production не подтверждён.
Это серверный компонент [P0.7](../TASKS.md), а не завершение всей стабилизации.

## Хранилище и мутации

[Миграция 0019](../migrations/0019_state_tombstones.sql) добавляет nullable
`user_kv.deleted_at`; существующие payload и версии остаются прежними.
NULL означает живую запись, числовая отметка — tombstone. Удаление очищает
v до пустой строки и сохраняет строку с увеличенной версией.
PUT с совпадающей версией tombstone восстанавливает значение и повышает версию.

| Операция | Условие | Результат |
|---|---|---|
| PUT, baseVersion=0 | Ключ никогда не создавался | Живое значение, версия 1 |
| DELETE, baseVersion=0 | Ключ никогда не создавался | Tombstone, версия 1 |
| PUT/DELETE, baseVersion>0 | Совпадает текущая версия живой записи или tombstone | Следующее поколение |
| baseVersion=0 при существующем поколении | Включая tombstone | 409, без мутации |
| Положительная версия отсутствующего ключа | Нет такого поколения | 409, version=0, exists=false |
| Устаревшая версия или исчерпанный безопасный диапазон | CAS не выполняется | 409, без мутации |

Повтор DELETE с уже использованной baseVersion конфликтует. DELETE с новой
совпадающей версией tombstone создаёт следующее поколение удаления.
Потеря ответа не разрешает клиенту вычислить подтверждение как baseVersion+1.

[state_store.ts](../functions/api/_lib/state_store.ts) проверяет весь пакет
одним условным SQL с материализованной проверкой конфликта. CAS и RETURNING
относятся к одной мутации. Диагностическое чтение при 409 может увидеть
ещё более новое состояние; оно никогда не используется как ack.
SQL-ошибка откатывает statement; нулевые changes не трактуются как ошибка
для отката отдельных statements в D1.batch.

Безопасные целые версии ограничены Number.MAX_SAFE_INTEGER; исчерпанная
версия не сбрасывается и не переполняется. Максимум 32 элемента PUT даёт
99 параметров; более крупный запрос получает TOO_MANY_ITEMS до записи.
Клиент должен разбивать независимые операции, сохраняя их намерение.
Это следует из [лимита D1](https://developers.cloudflare.com/d1/platform/limits/).
Семантика ответа: [SQLite RETURNING](https://www.sqlite.org/lang_returning.html).

## Чтение, экспорт и перенос аккаунта

Обычный GET возвращает только живые записи. `includeDeleted=1` возвращает
также `{ value: "", version, exists: false }`. Префикс сравнивается буквально,
без LIKE wildcard. Заголовок `X-FitFocus-State-Protocol: 2` позволяет новому
клиенту проверить поддержку контракта: одного пустого списка недостаточно,
поскольку старый сервер игнорирует неизвестный query parameter.

[Экспорт](../functions/api/_lib/user_data_export.ts) сохраняет version,
exists и deleted_at, не возвращая очищенный payload.
[Legacy-перенос аккаунта](../functions/api/_lib/legacy_sync.ts) копирует
живые записи и tombstones только на отсутствующие целевые ключи; поколения
разных владельцев не сравниваются и существующее значение не перезаписывается.
[Полное удаление аккаунта](../functions/api/_lib/account_delete.ts) намеренно
физически очищает все его user_kv, включая tombstones; другие аккаунты остаются.
Произвольный TTL/сборщик tombstones не добавлен.

## Условия выпуска и отката

1. Проверить новый клиент: он читает поколения tombstones, сохраняет 409-intent
   и использует подтверждённую DELETE-версию. Старый sender пока этого не умеет.
2. Применить additive-миграцию 0019 до серверного кода, проверив нужный D1 binding
   и восстановление данных. Отсутствие колонки не включает физический DELETE.
3. Остановить старые серверные writers и ограничить доступ несовместимых клиентов
   проверяемым способом. Unversioned DELETE существующего ключа теперь получает
   409; обычный reload или флаг сам по себе не доказывает остановку старой вкладки.
4. На отдельном staging проверить API, старую/новую сборку, перенос аккаунта,
   экспорт, hard delete и все пункты [чек-листа](../RELEASE_CHECKLIST.md).
5. Только после этого фиксировать release SHA и выпуск.

Версии защищены от повторного использования после перехода на новый writer.
Миграция не восстанавливает поколения, уже физически удалённые старым сервером.
Для старых pending/legacy операций без доказанной принадлежности поколению
до переключения нужна отдельная проверка/разрешение конфликта; нельзя считать
совпавшее число доказательством и автоматически повышать baseVersion.

Откат на старый физический DELETE разрушает гарантию. Сохранить колонку,
tombstones и очередь; при необходимости остановить записи и использовать
совместимый сервер. Восстановление старой копии не должно стирать новые мутации.
Сам факт preview deploy не подтверждает отдельную staging-БД или миграцию.
