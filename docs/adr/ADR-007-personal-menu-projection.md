# ADR-007: личные покупки как проекция принятого profile

Дата: 12.10.2026. Статус: реализовано в ветке на
[`4736ff5`](https://github.com/Michael-edel/FitFocus/commit/4736ff51b06f0062a6cb45a98169f4a4d0c39895); полная приёмка,
CI нового HEAD, staging и выпуск ещё проверяются. Локальная browser matrix
`4736ff5` прошла: 236 passed / 9 skips; серверная валидация дополнена на `830caf4`
и проверена 976 unit-тестами и повторным локальным Worker/D1 smoke.
Контракт и доказательства: [личное меню и покупки](../personal-menu-projection.md).

## Контекст

Недельное меню хранится внутри profile, а личные покупки ранее сохранялись
отдельным непостоянным POST. Session guard защищал владельца HTTP-запроса,
но не причинный порядок profile и покупок. Crash между commit и POST терял
доставку; поздний POST мог заменить покупки независимо от profile CAS.

## Решение

Profile остаётся источником личного меню и ингредиентов. Единственная
IDB-outbox доставляет его CAS-операцию. В том же SQL statement AFTER-triggers
сохраняют серверную проекцию по аккаунту и неделе. При отказе триггера профиль
не принимается. Ack подтверждает свою primary-строку через `RETURNING version`,
а не число изменений, включающее triggers.

Чтение и CSV используют каноническую проекцию. Только отсутствие её строки
разрешает legacy fallback. Пустая генерация и удаление текущего меню не дают
старым покупкам появиться вновь. Снимки прежних недель сохраняются.
Личный items POST отклоняется; семейный путь этим решением не переработан.

Новая write-capability объявляется после миграции; клиент проверяет её до AI
и отправки profile. Без неё локальные операции остаются в outbox, а guarded
чтение чистого profile сохраняет прежний контракт.

## Рассмотренные варианты

Отдельная постоянная items-операция потребовала бы второго ресурса, версии,
claim/finish, связи с profile и восстановления частичного успеха. При текущем
владении меню внутри profile это дублирует источник. Использование только
session scope или Web Locks не устраняет crash между запросами и серверную
перестановку. SQL-проекция связывает результат с уже принятым profile CAS.

## Следствия и выпуск

Добавляется D1-таблица с историей по неделям; она включается в экспорт,
удаление аккаунта и schema/privacy guards. Форма меню должна содержать
weekStart и массив shoppingListItems; недостающие значения legacy не угадываются.
Проверки схемы теперь сравнивают также SQL triggers/views.

Подготовительный сервер с `RETURNING` должен предшествовать 0020, сохраняя
прежние readers/writers до миграции. Затем выпускаются сервер проекции и
новый клиент после capability smoke. Прямой откат на старый reader без
учёта канонических снимков не считается безопасным. Реальный совместимый
выпуск, старые сборки и откат проверяются отдельно на staging.

Решение сохраняет [ADR-005](ADR-005-durable-outbox.md): одна очередь в IDB,
постоянный accountId операции, транзакционные claim/finish и необязательные
Web Locks. P0.5, P0.8, семейные writers и общий выпуск остаются открытыми.
