# ADR-008: семейное меню как одно версионированное поколение

Дата: 12.10.2026. Статус: принято для реализации в `fix/durable-outbox`;
выпуск ещё не принят. [Контракт и проверки](../family-menu-state.md).

## Проблема

Отдельные family menu/items HTTP-writers и серверный генератор не задают
порядок конкурирующих изменений. Session guard проверяет вход, но не защищает
от замены меню со старой базой или покупок от другой генерации. Отмена HTTP
не подтверждает откат SQL, а временный вызов не сохраняет намерение при reload.

## Решение

Хранить меню, порции и структурированные покупки одним JSON-поколением
с ключом family/week и CAS-версией. Принимать запись одним SQL statement
с `RETURNING version`, явной целью и повторной проверкой активного членства.
Покупки читать из этого снимка. Серверную генерацию сделать чистым preview.

Клиент сохраняет одно семейное намерение в существующей IDB-outbox;
claim/finish, auth-fence, causal children и конфликт используются совместно
с profile/state. Не вводить отдельную семейную очередь или items writer.
Для меню без облачной семьи использовать guarded profile commit.

Миграция 0021 сохраняет legacy JSON и вводит SQL-барьер прежних writers.
Клиент поднимает IDB до v3: v2 sender не знает семейный маршрут и иначе мог бы
подтвердить новый ресурс через generic state. Дополнительно generic endpoint
запрещает семейный ключ. Web Locks не выбирают хранилище или версию протокола.

## Отклонённые варианты

- Только login guard: не решает stale-base и соответствие menu/items.
- Два outbox intents: допускают промежуточное и конкурирующее состояние.
- Только отключить старый writer в новой сборке: ранее открытые сборки
  продолжают работать; нужны SQL-барьер и versioned IDB opens.
- Fallback к legacy при пустом/corrupt canonical: восстанавливает старые покупки
  и скрывает повреждение данных.

## Последствия и приёмка

Конфликт остаётся явным и сохраняет локальное намерение. Старый клиент
не может записывать через прежние family endpoints после 0021. Совместимый
rollback должен понимать canonical reader и IDB v3; downgrade/delete не нужен.
Недостающая часть миграции не публикует capability и не включает старый writer.

Нужны реальные old/new bundles на одном origin, lifecycle на устройствах,
проверка legacy-данных, восстановление corrupt/conflicted записей, staging и
rollback artifact. Наличие SQL/IDB unit-тестов не закрывает эти критерии.
Защищённая main и production этим решением не изменяются.
